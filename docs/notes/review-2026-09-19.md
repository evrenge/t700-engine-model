## 1. The one red test

`validation/test_appendix_b_elements.py::test_the_three_dof_fuel_column_against_b7_b9_b11[3]`

Descent 3-DOF `b` column against printed B11, as a ratio:

| trim | b(NG) | b(NP) | b(T41) |
|---|---|---|---|
| hover | 0.9762 | 0.9750 | **0.8716** |
| level 80 kt | 0.9897 | 1.0077 | 0.9775 |
| descent 80 kt | 1.0037 | 0.9390 | **0.8527** ← outside the 0.86 floor |

Band is `THREE_DOF_B = (0.86, 1.02)`. The miss is 0.0073, 4.6 % of the band's width.

**It is not one bad element — the whole T41 row sits low.** Hover's 0.8716 is only 0.0116
inside the same floor. The user's instinct in the prompt above is the right lead.

Went red at `22fd83f` when A11 took the arc frame model under the automatic held-out rule.
Pinning A11 back to straight was measured and gives 0.8635, inside. Both readings and the
numbers for each are in open question **#73**; related: **#31** (the unprinted heat-sink time
constants) and **#43** (the interpolation ambiguity).

Leads worth chasing that nobody has:
* the 3-DOF **state ordering is inferred, not printed** — `{NG, NP, T41}`, from three pieces
  of evidence in `docs/notes/inventory-appendix-b.md` §2.4, and `appendix_b.py` carries
  `states_are_printed=False` for exactly these models. The 3-DOF and 6-DOF blocks are also
  the only two with **no printed eigenvalues** to corroborate them, and they are the two
  blocks that got worse on this branch while 2-DOF and 5-DOF improved.
* `f_hs` (A11) costs **exactly 0.000 %** at every trim and shows up only in transients — it
  sets a heat-sink time constant that does no work at equilibrium. Yet it is the map whose
  calibration moved the T41 row. Understand that path before changing anything.

## 4. Bugs — none fixed

Attribution matters here: roughly half are in code written or touched during this branch.

### Ours, introduced on this branch

1. **`tools/figure/glyph.py:179` and `:30` — `max_move` is per round, not from the seed.**
   `c0 = C[i].copy()` sits inside `for it in range(rounds)`, so with `rounds=4` a marker can
   walk 40 px in 10 px steps untripped. The *behaviour* is inherited (identical in
   `94ccdda^`); the docstring claiming "from its seed" is new, in two places, and so is
   recipe trap 9's wording. This guard was reported to the user as delivered. It is not.
2. **`tools/figure/raster.py:68` — `render()` is dead** and its docstring names A1 as its
   caller. `digitize_a1.ensure_page()` shells out to `pdftoppm` itself and re-implements
   `load_gray` inline at line 138. The sixth copy of the raster the consolidation set out to
   remove is still there, with the replacement unused beside it. Its cache key is the stem
   only, so a second call at another dpi would return the first dpi's file.
3. **`tools/compare_models.py:81` — the docstring claims a held-out lattice choice the code
   never makes.** `edge_positions(fine=True)` takes the fine lattice unconditionally; four
   shipped axes are on majors. Its numbers therefore describe a configuration that is not
   what ships. **It changed no decision** — both tools pick A10, A11, C26 for arcs — but the
   table shown to the user was not measured on the shipped calibration.
4. **`tools/figure/ticks.py:72` — `n_majors` dead**, zero callers.
   **`tools/figure/glyph.py:257` — `glyph_only_windows(seglen=…)` accepted and ignored.**
   Both violate CLAUDE.md's "no abstraction added for later".
5. **Three stale trap-7 citations** still asserting, in the present tense, the claim the
   recipe reversed: `tools/figure/__init__.py:12`, `tools/figure/frame.py:23`,
   `tools/compare_models.py:11` and `:291`. These are the reader's entry point to the library.
6. **`tools/sensitivity_sweep.py:45` omits `f7`** while the docstring says "every map, both
   axes". `f7` has the same `x,y,sx,sy` shape as `f2`. A7's own docstring puts it at +2.9 to
   +5.5 % SHP per +1 %, which would top the table. `docs/notes/digitizing-recipe.md`'s
   sensitivity table inherits the omission and presents itself as complete.
7. Smaller: `tools/figure/frame.py:265` cites trap 9 where the rewritten recipe numbers it

### Inherited, found now

8. **`tools/figure/ticks.py:215` — `edge_run` and `find_ticks` ignore `sign` entirely.**
   `abs(p - m) + 1` cancels it. Verified: `sign=+1` and `sign=-1` give bit-identical arrays
   and the same 169 ticks on p.63's left edge, while `protrusion` on the same edge gives
   2863 vs 1290. So the shared `EDGE` table feeds one sign-critical consumer and one
   sign-blind one — a corrupted sign is catastrophic in `majors_all_edges` and undetectable
   in `fine_lattice_all`. Also: ink *outside* the frame registers as a tick.
9. **`tools/digitize_single_curve.py:1003,1017` — every single-curve CSV labels its per-edge
   axis maps with the wrong edge.** One `side` dict serves two meanings; for x the maps come
   from the bottom/top edges and print as `left`/`right`. Wrong in all 13 files. `f7`'s
   hand-written header has it right.
10. **`tools/figure/provenance.py:131,116` — `parse_calibration` takes the first regex match
    as the frame, and `parse_poly` silently degenerates.** Confirmed:
    `parse_poly('+0.5503129 u +0.29944711', 'y')` returns `[0.84976]` — two coefficients
    summed into a constant, no error. Combined with 9, reordering a header's blocks makes
    `check_straightness` fit an axis map as a frame line and report garbage rather than
    raise. Cheap detection: `edge_str` always emits a slope term, so a length-1 result is
    always a failed parse.
11. **`tools/digitize_single_curve.py:1151` — six of thirteen headers publish "a 7x7
    morphological OPENING"** while those figures set `open_sz=6` (a3, c24, c25, c27, c28,
    c29). `seeds()`'s own docstring says a 7×7 opening erases C24's ninth marker.
12. **`tools/digitize_multi_curve.py:133` — `v = 0 at the TOP`** in `blobs()`/`trace()`,
    against the library's and its own `main()`'s `v = 0 at the bottom`. A reviewer measured
    that C30's declared legend box is consequently inverted, contaminating the "70 of 410
    columns" justification in the docstring (re-measured: 52 with the declared box, 146 with
    it flipped). **Blast radius is the `--probe c30` path only** — `digitize_c30.py` has its
    own legend mask and reproduces byte for byte.

### The numerical inconsistency

13. **`tools/figure/axis.py:294` — `axis_values` builds coordinates with `make_sv` even for
    `frame_order=1`, while `digitize_single_curve._calibrate_under` and
    `compare_models.plot_coords` use a homography.** For four straight edges those are not
    the same map. Measured over f8's plot interior on a 25×25 grid:
    `max|u_sv − u_homography| = 1.10e-3`, which is **0.022 in A2's PS3/P2 units** — larger
    than A2's own quoted 0.0155 integer-lattice accuracy check. So the `fo=1` entries in A2's
    and A9's published model-spread are not the model the other family runs. Affects an
    uncertainty term, not a value.

## 6. Documentation state

Measured density: **`src/t700` 49 %**, `tools` 25 %, `tests` 36 %, `validation` 36 %
explanatory lines against code lines.

The user's verdict, which stands over mine: this is too much, it should be summarised, lean
and to the point, and it is to be trimmed — **but only after they have read it. Do not touch
any documentation yet.**

My own finding, which is a different problem from volume and is not fixed by trimming:
**the mechanisms here catch numbers that drift and do not catch claims that were never
true.** `test_scope_tolerances` compares numbers and ignores rows it never saw.
`test_determinism` compares runs and ignores processes. `test_tool_duplication` compares
bodies and ignores `validation/`. On top of that, this branch added false claims: a docstring
naming a caller that does not exist (2), one describing a selection never made (3), one
promising a guard not enforced (1), a citation to a test that does not exist (23), and a
"three holes closed" note over a fourth hole of the same shape (20). Several were untrue when
written, including in the commit messages that described the fixes.

Two candidate mechanisms, neither built:
* make a measurement quoted in prose fail the suite when it drifts — the trick
  `test_scope_tolerances.py` plays on the Tolerance column, applied to "measured X" claims;
* make a cited test name fail the suite when no such test exists.
